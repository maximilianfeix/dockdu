# Demo and prune measurements, 2026-10-14

Every number on the README first screen, in the GIF (`docs/demo.gif`, `demo.tape`) and in the article ([../articles/docker-disk-usage-vs-prune.md](../articles/docker-disk-usage-vs-prune.md)) comes from this file.

## Environment

- **Host:** macOS arm64 with Docker Desktop. Each test daemon ran in its own disposable container (`docker run --privileged --rm docker:29-dind` or `docker:28-dind`), so no real workload was involved. The daemons and their images were removed afterwards.
- **Engine 29.9.0** (API 1.56): containerd image store (`DriverStatus` `driver-type io.containerd.snapshotter.v1`, driver `overlayfs`), the default on a fresh install.
- **Engine 28.5.2** (API 1.51): overlay2 graph driver.
- **dockdu:** v0.3.0, the linux/arm64 release archive, verified with `shasum -a 256 -c checksums.txt`.
- **Demo state:** `LOG_MB=500 scripts/demo-up.sh`.
  - One container writes 500 MiB to stdout with the default json-file driver, plus one bounded container (`--log-opt max-size=1m --log-opt max-file=3`).
  - A BuildKit build adds a 64 MiB layer of random data on top of `alpine:3.22`.
  - Compose project `dockdu-demo` has two services and a named volume holding 32 MiB, and there is one orphan volume.

`du` reports 535.1M for the log files and dockdu 537.0 MiB. `du -h` rounds to MiB-based units, and the two measure the same files; the 2 MiB difference is the bounded container's rotated files, which match `*-json.log.N` and so are not in `du`'s glob. `dockdu --disk` reports 784.0 MiB = 802,816 KiB for the data root; `du -sxk` reports 802,796 KiB.

## B. What `docker builder prune -af` actually freed

Each run used a fresh disposable daemon with a single build. The data root was measured with `du -sxk /var/lib/docker` right before and right after the prune.

| Engine | Image store | Shared build cache (dockdu) | `builder prune` printed | Freed on disk |
|---|---|---|---|---|
| 28.5.2 | overlay2 | 64.0 MiB | `Total: 67.11MB` | ≈ 0 (75,368 → 75,436 KiB) |
| 28.5.2 | overlay2 | 48.0 MiB | `Total: 50.33MB` | 28 KiB |
| 29.9.0 | containerd | 140.7 MiB | `Total: 147.6MB` | 74,480 KiB (72.7 MiB) |
| 29.9.0 | containerd | 108.7 MiB | `Total: 114MB` | 58,212 KiB (56.8 MiB) |
| 29.9.0 | containerd | 140.7 MiB (with the demo's logs) | `Total: 147.6MB` | 74,584 KiB (all of it under `containerd/`) |

**Reading:**
- **overlay2:** shared records cost nothing to prune and free nothing. Docker's "Total" counts their logical size anyway.
- **Containerd image store:** about half of the shared bytes were freed on disk, which suggests the build cache kept its own copy next to the image. These runs did not establish which store objects that copy consists of.

dockdu v0.2.0 printed "prune would NOT free 140.7 MiB" in the containerd case. That was wrong, and v0.3.0 replaced it.

In the run with the demo's logs, `docker system prune -f` afterwards reclaimed 0B. The 537 MiB of logs of the running container stayed, as expected: prune never touches the logs of existing containers.

## Reproduce

```
docker run -d --rm --privileged --name dockdu-dind-29 -e DOCKER_TLS_CERTDIR= docker:29-dind
docker cp dockdu dockdu-dind-29:/usr/local/bin/dockdu          # linux release binary
docker cp scripts dockdu-dind-29:/root/scripts
docker exec dockdu-dind-29 apk add bash
docker exec -e LOG_MB=500 dockdu-dind-29 bash /root/scripts/demo-up.sh
docker exec dockdu-dind-29 sh -c 'docker system df; dockdu --top 3; du -ch /var/lib/docker/containers/*/*-json.log | tail -1'
vhs demo.tape                                                   # re-records docs/demo.gif
docker stop dockdu-dind-29                                      # --rm removes it and its anonymous volume
```
